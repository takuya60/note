### 面试核心 Q1：你用 Buildroot，它到底帮你做了什么事？

**标准回答方向**：它帮我自动化完成了**四大件**的交叉编译。

很多对 Linux 了解不深的人以为 Buildroot 就是个做 "rootfs（根文件系统）" 的工具，其实不是。 Buildroot 的职责是**“从源码到镜像的自动化流水线”**，它按顺序干了四件事：

1. **构建交叉编译工具链 (Toolchain)**：它先下载 `gcc`、`binutils`、`glibc/musl` 源码，编译出能在 Ubuntu（x86）上跑，但生成 RK3568（ARM64）机器码的编译器。
2. **编译 U-Boot**：用刚做好的工具链去编译 Bootloader。
3. **编译 Linux Kernel**：用工具链去编译你配置好的内核。
4. **构建根文件系统 (Rootfs)**：下载 `BusyBox`、`Qt` 库等各种应用包，用工具链编译它们，最后按照 Linux 标准目录结构（`/bin`, `/etc`, `/usr` 等）把这些二进制文件塞进去，打包成一个 `.ext4` 或 `erofs` 的镜像文件。

**面试得分点**：点出"它首先也是最重要的工作是构建 Toolchain"，这说明你对底层是有认知的。

---

### 面试核心 Q2：你知道什么是交叉编译吗？为什么要交叉编译？

**标准回答方向**：宿主机架构与目标机架构不同，目标机资源不足以进行本地编译。

- **是什么**：在一种架构的机器上（比如你的 x86 Ubuntu），编译出另一种架构机器上运行的代码（比如 ARM64 的 RK3568）。
- **为什么**：RK3568 虽然性能不错，但如果你在它上面编译包含上千万行代码的 Qt 库和 Linux Kernel，可能需要十几个小时甚至死机（因为内存不够、IO 太慢）。用你电脑上强大的 CPU 和海量内存几十分钟就搞定了。
- **难点在哪**：环境变量的污染。如果你在 x86 上编译一段 C 代码，默认链接的是 x86 的 `libc.so`，放到 ARM 板子上运行必定报 `Exec format error`（执行格式错误）。所以必须使用专用的前缀工具链（比如 `aarch64-linux-gnu-gcc`）。

### 面试核心 Q3：根文件系统（Rootfs）里到底装了什么？什么是 BusyBox？

**标准回答方向**：它是内核挂载的第一个文件系统，提供了用户态的运行环境；BusyBox 是嵌入式的“瑞士军刀”。

- **Rootfs 是什么**：Linux 内核启动的最后一步，就是挂载根文件系统并执行里面的 `/sbin/init`（或者你指定的 init 进程）。如果没有它，内核就相当于一个没有躯干的大脑，报 `kernel panic - not syncing: VFS: Unable to mount root fs` 死机。
- **里面有什么**：C 运行库（libc）、设备节点（`/dev`）、配置文件（`/etc`）、应用程序和系统命令。
- **什么是 BusyBox**：在 Ubuntu 里，`ls`, `cp`, `cat`, `grep` 都是独立的可执行文件，每个好几百 KB，加起来极速膨胀。在嵌入式里，我们用 BusyBox 这样一个单独的可执行文件（不到 1MB），它内部集成了所有这些常用命令的功能。系统里那些 `ls`、`pwd` 等等，其实全部是**指向 BusyBox 这个单一文件的符号链接（软链接）**！

**面试得分点**：提到"命令全是 BusyBox 的软链接"，这说明你亲自看过嵌入式文件系统的结构。

### 面试核心 Q4：行业里还有 Yocto 或 OpenWRT，它们跟 Buildroot 有什么区别？为什么你选 Buildroot？

**标准回答方向**：Buildroot 简单直接适合深度定制，Yocto 庞大复杂适合大型协同。

这是非常进阶的问题，体现行业视野：

- **Buildroot**：基于 `Makefile`，设计哲学是**“简单、扁平化”**。选了什么包就编译什么包，产出一个镜像。不保留中间二进制，每次都要重新编译很多东西。**特别适合资源受限、需要极限裁剪的项目**（完美契合你的项目目标！）。
- **Yocto / OpenEmbedded**：基于 `Python` 和配方（Recipe）。设计哲学是**“模块化、分发”**。它像搭积木一样，能生成可以直接在板子上用 `apt` 或 `opkg` 安装的二进制包（`.rpm`或`.deb`）。非常庞大，学习曲线极陡峭，车厂的座舱系统（比如基于 AGL）经常用它。

**你的回答策略**："因为我的目标是把一个 200MB 的系统极限压榨到 8MB 以内，我需要对每一个引入的包拥有**上帝视角**的绝对控制力。Buildroot 的扁平化 Makefile 架构让我能清晰看到整个依赖树，没有任何隐藏的冗余组件，这使得它成为了我达成极限裁剪目标的最优解。"

### 面试进阶 Q5：你说你把内核从 15MB 裁剪到了 5MB，你知道这个 5MB 的文件最终是以什么格式烧进去的吗？`zImage` 和 `Image` 的区别？

**标准回答方向**：目标平台的架构决定了内核镜像的格式；ARM64 架构下通常是 `Image` 及其压缩形态。

- **内核编译产物**：当你 `make menuconfig` 并编译完内核后，最原始生成的是一个拥有完整调试信号量的 ELF 格式可执行文件叫 `vmlinux`（好几百 MB 大小，这玩意儿是给 GDB 调试用的，不可能烧进板子）。
- **去符号化**：编译系统会把 `vmlinux` 用 `objcopy` 去掉符号表等调试信息，生成一个纯正的机器码文件（叫 `Image`，通常十几 MB）。
- **`zImage`（ARM32 常见）**：把这个 `Image` 压成 gzip 等格式，然后在头部加上一段**自解压代码**。系统上电跑到这里时，先运行头部代码把内核解压到内存，再跳到解压后的内核入口启动。
- **RK3568 (ARM64) 常见**：由于 ARM64 内存极大，现在很多做法是直接烧写无压缩的 `Image`，或者直接压缩后加上头信息成为针对 u-boot 格式的 `uImage` 或打包进 `boot.img` 里面。

**面试得分点**：说明 `vmlinux` -> `Image` -> `zImage` 的层级关系，表明你了解内核从源码到二进制究竟经历了怎样一层层的剥茧抽丝。

### 面试进阶 Q6：你在内核裁剪时，怎么判断一个驱动是该裁剪掉（去掉），还是编译进内核（Built-in），还是编译成模块（Module, `.ko`）？

**标准回答方向**：按启动需求和资源约束区分。

对于内核里面的选项，在 `menuconfig` 里有三个状态（`N`, `Y`, `M`）：

1. **`N` (不选, 裁剪掉)**：板子上压根没有这个硬件，或者你的业务场景绝对用不到（比如这个没有网络需求的纯本地显示控制板可以去掉 IPv6）。
2. **`Y` (Built-in, 编译进 zImage/Image 中)**：也就是这个驱动代码会跟内核核心代码**死死绑在一起**。这一般留给**系统启动必须要用到的关键驱动**。例如 eMMC 存取驱动、EXT4 文件系统驱动，如果把这些编成模块放在 eMMC 文件里，内核一启动，自己的肚子里没自带读文件系统的能力，它就读不到那个存放模块的文件，这叫"先有鸡还是先有蛋"死循环，直接内核宕机。
3. **`M` (Module, `.ko` 动态加载模块)**：不会占用内核镜像自身的体积，而是在根文件系统启动后，或者等对应的硬件热插拔（比如 U盘）时，由 `insmod` / `modprobe` 动态加载到内存中去执行。**适合体积大、又非关键启动所必需的东西（例如摄像头驱动、你手写的 UART Line Discipline 和 传感器驱动等）。**

**你的绝杀回答**："为了把内核镜像体积压到极限的 5MB，我把大量非启动必需的驱动全都变成了 `.ko` 甚至剔除（N）。我只让必须要亮灯、出画，以及读取根文件的驱动保留为 `Y`。把驱动延后用模块（M）加载，极大地去掉了内核早期初始化的耗时，这才帮我做到了上电 5 秒内出 UI 的极速启动。"

### 面试进阶 Q7：设备树（Device Tree / DTS）到底是个什么鬼东西？为什么要发明它？

**标准回答方向**：它是一份只描述板级硬件信息的"说明书"，负责把硬件信息和内核代码解耦。

- **为什么要有它？** 在 Linus Torvalds 发过一次名震开源界的火（"ARM Linux代码成了垃圾堆"）之前，所有具体的板子上的寄存器基地址、那个脚接什么传感器、GPIO 初始高电平还是低电平，都**硬编码写死**在 C 代码里的（早期的 `arch/arm/mach-xxx` 目录）。这导致只要新出一块板子，内核里就要堆进一堆毫无逻辑价值只包含地址和变量的垃圾 C 代码。
- **设备树的改变**：内核把所有带有具体 IO 信息的配置抽离出来，变成了一种树状的类似 JSON 的文本描述文件（`.dts`）。
- **编译链条**：`.dts` 用 `dtc` 工具编译成二进制的 `.dtb` 文件。
- **启动阶段工作流程**：U-Boot 在加载完内核（`Image`）后，也会加载这个 `.dtb` 到一块特殊的内存，然后执行内核代码时把首指针告诉内核；内核在初始化过程中就不再猜自己跑在什么板子上，而是去解析这个 DTB 树，找到上面挂了哪些 I2C 节点、哪个 GPIO 是背光控制！

**面试得分点**："设备树的本质是为了把**'硬件静态描述'**从**'内核驱动的动态执行代码'**中解耦抽离出来..." 这种有高度的词一出，面试官大概率频频点头。

### 面试进阶 Q10：中断处理的上半部和下半部是什么？为什么要分？

你的 UART 驱动和 I2C 驱动都涉及中断，这题几乎必问。

**为什么要分两半？**

当硬件触发中断时（比如 UART 收到一个字节），CPU 会**暂停当前的一切工作**去执行你的中断处理函数。在这段时间里：

- 其他中断可能被屏蔽（收不到）
- 进程调度被暂停（系统像"卡住"了）

所以中断处理必须**极快极快**，不能在里面做耗时操作。

**下半部的三种实现方式**（面试追问点）：

|方式|特点|适用场景|
|---|---|---|
|**softirq**|最快，但只能静态注册（内核编译时确定）|网络栈、块设备等核心子系统|
|**tasklet**|基于 softirq，可以动态注册|简单的驱动|
|**workqueue（工作队列）**|在内核线程上下文执行，**可以睡眠**|需要调用可能阻塞的函数时（如 I2C 传输）|

### 面试进阶 Q11：内核里的锁机制有哪些？`spinlock` 和 `mutex` 的区别？

你的驱动里一定会涉及并发（比如中断上下文往缓冲区写数据，用户进程从缓冲区读数据），面试官会问你怎么保护共享数据。

||spinlock（自旋锁）|mutex（互斥锁）|
|---|---|---|
|**等待方式**|**忙等（spin）**，CPU 不停循环检查锁有没有释放|**睡眠等待**，拿不到锁就让出 CPU 去调度别的进程|
|**能否睡眠**|❌ 持有 spinlock 期间绝对不能睡眠！|✅ 可以|
|**适用上下文**|中断上下文 + 进程上下文|**仅进程上下文**（因为中断里不能睡眠）|
|**适合场景**|保护极短的临界区（几行代码）|保护可能耗时的操作（如 I2C 传输）|

**经典面试陷阱题**："你能在中断处理函数里用 mutex 吗？" **答**：绝对不能！因为 mutex 在拿不到锁时会让当前执行流睡眠，而中断上下文没有对应的进程，无法被调度，直接内核 panic。中断里只能用 spinlock（而且要用 `spin_lock_irqsave` 变体来同时屏蔽本地中断）。

**结合你的项目**：

> "在我的 Line Discipline 驱动中，`receive_buf` 是在软中断上下文被调用的，而 `read` 是在进程上下文被调用的。两者共享一个环形缓冲区，我使用 `spin_lock_irqsave` 来保护对缓冲区读写指针的访问，确保在锁内不会发生睡眠。"

## 回答你的问题：不想要 Qt，改谁？

**改 Rootfs（Buildroot 的配置）**，因为 Qt 是一个用户态的**应用程序库**，它跟"水电管道"（内核）没有任何关系。

具体操作：

bash

# 进入 Buildroot 的配置菜单

cd buildroot

make menuconfig

# 找到 Target packages → Graphic libraries → Qt5

# 把勾去掉，保存退出

# 重新编译 rootfs

make

内核完全不用动，因为内核根本不知道也不关心上面跑的是 Qt 还是别的什么应用。

## 反过来的例子

如果你想去掉**蓝牙功能**，那两边都要改：

1. **Kernel**：去掉 `CONFIG_BT`（蓝牙协议栈驱动）
2. **Rootfs**：去掉 `bluez`（蓝牙用户态工具包）

因为蓝牙既需要内核里的驱动支持（管道），也需要用户态的控制工具（家电）。

---

这样你就能理解为什么我们的裁剪计划是**两条线并行**的了：

- **内核裁剪**：用 `make menuconfig`（kernel 目录下），去掉无用的驱动和协议
- **Rootfs 裁剪**：用 `make menuconfig`（buildroot 目录下），去掉无用的应用和库
