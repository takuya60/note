### 第二部分：扒开办事窗口 `evdev.c` 的底裤

在输入子系统里，`evdev.c` 是绝对的 C 位。它就是内核给你写好的“通用办事窗口”。你的 App 想要拿数据，全都得找它。

我们来看看这个窗口的 **5 个核心业务流程（对应课里的 5 个函数分析）**：

#### 1. `evdev_connect`：相亲登记与建档

- **触发时机**：你在驱动里调用 `input_register_device()`，内核发现你的按键（男嘉宾）和 `evdev`（女嘉宾）匹配成功时。
    
- **它偷偷干了啥**：
    
    1. **领结婚证**：在内存里 `kzalloc` 分配一个 `evdev` 结构体，并把你的硬件和它死死绑在一起（生成 `input_handle`）。
        
    2. **分配门牌号（分配设备号）**：系统里有一个全局数组（一般有 32 个坑位）。`evdev` 会去遍历这个数组，找到第一个没人的坑位，比如找到了 1 号坑，那你的**次设备号（minor）**就是 1。
        
    3. **建实体大门**：根据刚才的次设备号，调用内核底层 API 在 `/dev/input/` 目录下动态生成一个叫 **`event1`** 的文件！
        

#### 2. `evdev_open`：接待大厅开门

- **触发时机**：写 App 的程序员在 C 语言里敲下 `open("/dev/input/event1", ...)` 的瞬间。
    
- **它偷偷干了啥（极其精妙的设计！）**：
    
    - 假设有 3 个不同的 App（比如桌面系统、按键精灵、测试工具）**同时**打开了 `event1` 怎么办？数据给谁？
        
    - `evdev_open` 的绝招是：**来一个客户，我就建一个专属小房间！**
        
    - 每次执行 `open`，它会在内核里分配一个叫 **`evdev_client` (客户端)** 的结构体。最牛逼的是，这个结构体里自带了一个 **环形缓冲区 (Ring Buffer)** 。
        
    - 所以，3 个 App 打开，就有 3 个独立的缓冲区。互不干扰！
        

#### 3. `evdev_read`：客户在窗口等快递

- **触发时机**：App 程序员敲下 `read(fd, &ev, ...)`。
    
- **它偷偷干了啥**：
    
    - 它会去检查刚才给这个 App 分配的专属“环形缓冲区”里有没有数据。
        
    - **有数据**：用 `copy_to_user()` 把数据从内核态安全地拷贝给 App，直接下班返回。
        
    - **没数据（高能预警）**：如果此时没人按按键，难道让 `read` 函数死循环空转把 CPU 烧掉吗？绝对不行！`evdev_read` 会调用内核的休眠神技 `wait_event_interruptible()`。
        
    - **后果**：你的 App 进程会瞬间进入**休眠状态（S 状态）**，彻底交出 CPU 的控制权，直到有人把它叫醒。
        

#### 4. `evdev_event`：快递员分发包裹

- **触发时机**：硬件中断触发了，你在底层驱动调用了 `input_event(...)`。
    
- **它偷偷干了啥**：
    
    - 它收到了你传来的 `EV_KEY`、`KEY_ENTER`、`1` 这三个数据。
        
    - 它加上系统当前的时间戳，打包成标准结构体 `struct input_event`。
        
    - 然后，它顺着链表找到所有打开了这个设备的 `evdev_client`，**把这个结构体塞进他们每一个人的环形缓冲区里！**
        

#### 5. 唤醒机制（闭环！）

- **触发时机**：当你在底层驱动调用 **`input_sync()`** 时！
    
- **它偷偷干了啥**：
    
    - `input_sync()` 在底层也会变成一个事件发给 `evdev`。
        
    - `evdev` 收到同步信号后，会大吼一声，调用 `wake_up_interruptible()`！
        
    - **奇迹发生**：刚才在 `evdev_read` 里因为没数据而呼呼大睡的 App 进程，被瞬间叫醒！App 一睁眼发现缓冲区里有数据了，美滋滋地拿走数据，继续往下跑代码。

### 第三部分：顺藤摸瓜（一次点击的终极奇幻漂流）

这部分讲的是**“一条数据是怎么从你的底层驱动，一步步跑到 `evdev` 里的”**。

在内核源码里，这个流程堪称教科书级别的解耦（分层）设计。我们用一根线把它穿起来：

#### 第一站：你的驱动（起点）

你的手按下了 RK3568 开发板上的按键。触发 GPIO 中断，进入你的中断处理函数。 你敲下： `input_event(my_button_dev, EV_KEY, KEY_ENTER, 1);`

#### 第二站：Input Core 核心层（安检与路由）`input.c`

`input_event()` 这个函数其实是在 `input.c` 里定义的。它收到你的数据后，干了两件极其重要的大事：

1. **安检（过滤假数据）**： 它会偷偷去翻你的男嘉宾简历（上一节我们讲的 `evbit` 和 `keybit` 位图）。 _核心源码逻辑_：`if (is_event_supported(code, dev->keybit, KEY_MAX))` 如果它发现你根本没注册过 `KEY_ENTER` 却发来了回车键，它会直接 `return` 丢弃，根本不往下传！
    
2. **路由寻址**： 安检通过后，它调用内部核心函数 `input_pass_values()`。这个函数的作用是：“顺着结婚证（`input_handle`），找到所有跟你绑定的女嘉宾（`handler`）”。
    

#### 第三站：抵达 Event Handler 处理层 `evdev.c`

`input_pass_values()` 找到了 `evdev_handler`，并且毫不留情地调用了女嘉宾的接收函数： `handler->event(handle, type, code, value);`

**轰！这就完美衔接到了我们第二部分讲的第 4 步（快递员分发包裹）！**数据被成功塞进了环形缓冲区，并最终唤醒了用户态的 App。

### 💡 极简总结：一张图刻在脑子里

你不需要记源码，你只需要在脑子里形成这样一个流水线：

`硬件中断` ➡️ `你的驱动: input_event()` ➡️ `核心层 input.c (过安检)` ➡️ `处理层 evdev.c (填入环形缓冲区 + wake_up唤醒)` ➡️ `用户态 App: read() 从睡眠中醒来拿到数据`。

整个流水线行云流水，没有任何一个环节在浪费 CPU 的资源。这才是 Linux 架构真正的魅力！

现在，代码底裤都给你扒光了。你在日常写代码时，有没有想过一个极其现实的问题：**如果用户态的 App 读数据的速度太慢，而你手速单身二十年，疯狂按按键，那个“环形缓冲区”被塞满溢出了，Linux 内核会怎么处理？**（这可是高级调试时经常会遇到的丢键现象！）
