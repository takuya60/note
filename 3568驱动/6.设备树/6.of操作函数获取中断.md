之前的“物业和住户”的比喻你还记得吧？

在设备树（`.dts`）里，住户（外设）写下了报警表格：`interrupts = <9 0>;`，意思是“我接在物业的 9 号引脚上，低电平触发”。这只是写在纸上的静态文本。

现在，**女嘉宾（你的 C 语言驱动代码）出场了。在 `probe` 函数里，她必须把纸上的 `<9 0>` 翻译成 Linux 内核真正能认的“系统中断号”**，然后才能去申请中断。

这套把“纸质表格”变成“系统中断号”的绝技，就是 **of 中断操作函数**。

我为你详细拆解这个过程和最核心的 API：

---

### 一、 核心痛点：为什么要“获取”和“映射”？

你必须要明白一个内核设计的底层真相：**硬件中断号 $\neq$ 软中断号（虚拟中断号）。**

- **硬件中断号 (Hardware IRQ)**：就是物理连线。比如接在 GPIO1 的第 9 个引脚，硬件号就是 9。
    
- **虚拟中断号 (Virtual / Linux IRQ)**：Linux 内核管理着成千上万的中断（CPU内部的、I2C的、网卡的、各个GPIO的）。为了不打架，内核设计了一个 **IRQ Domain（中断域）** 机制，给每一个硬件中断重新分配了一个全系统唯一的身份证号（比如分配成了 145 号）。
    

**所以，of 中断提取函数的核心任务就两个：**

1. **Parse（解析）**：去设备树里把 `<9 0>` 读出来。
    
2. **Map（映射）**：向内核的 IRQ Domain 申请，把硬件号 9 映射成一个唯一的软中断号（比如 145），并返回给你。
    

---

### 二、 绝对主力 API：`irq_of_parse_and_map`

这是处理设备树中断最经典、最底层的函数。可以说它把脏活累活全包了。

#### 1. 函数原型

C

```
unsigned int irq_of_parse_and_map(struct device_node *dev, int index);
```

#### 2. 参数拆解

- **`dev`**：就是你外设的那个设备树节点指针（`device_node`）。告诉内核去哪个节点里找 `interrupts` 属性。
    
- **`index`**：索引号。为什么要这个？因为有些复杂的设备会接**多根中断线**！
    
    - 比如一个串口芯片，可能有一根线专门报接收中断，另一根线报发送中断，设备树里会写两组数据：`interrupts = <9 0>, <10 0>;`。
        
    - 传 `0`，内核就帮你解析并映射第一组 `<9 0>`。
        
    - 传 `1`，内核就帮你解析并映射第二组 `<10 0>`。
        

#### 3. 返回值

- 成功：返回内核分配好的**虚拟软中断号**（比如 145）。
    
- 失败：返回 0（在 Linux 中断体系里，0 通常代表无效的 IRQ）。
    

---

### 三、 现代驱动的“偷懒绝招”：`platform_get_irq`

虽然上面那个 `irq_of_parse_and_map` 是底层的真正干活者，但在现代的 Linux 驱动开发中（特别是结合了你刚学的**平台总线**），我们其实**很少直接调用它**。

内核为平台设备（`platform_device`）提供了一个极其方便的封装函数：

C

```
int platform_get_irq(struct platform_device *dev, unsigned int num);
```

**为什么它更好用？**

因为只要你用的是平台总线，当你调用这个函数时，它底层会自动去调用 `of_` 相关的函数帮你解析设备树，而且它的错误处理更完善。

---

### 四、 实战演练：在 `probe` 函数里怎么写？

结合你手头的 RK3568 开发板，标准的现代写法是这样的：

C

```
static int my_driver_probe(struct platform_device *pdev)
{
    int irq; // 用来装系统分配的虚拟中断号
    int ret;

    printk("准备提取中断资源...\n");

    // 【核心动作】：提取第 0 个中断资源
    // 这一步底层已经帮你完成了 Parse (读设备树) 和 Map (分配虚拟号)
    irq = platform_get_irq(pdev, 0);
    
    // 错误校验机制
    if (irq < 0) {
        printk("糟糕，没在设备树里找到中断信息！\n");
        return irq; 
    }

    printk("提取成功！硬件中断被映射为了系统软中断号: %d\n", irq);

    // 【下一步】：拿到软中断号后，向内核正式注册中断处理函数
    ret = request_irq(irq, my_irq_handler, IRQF_SHARED, "my_device_irq", pdev);
    // ...
    
    return 0;
}
```

### 总结归环

其实说到这里，我们已经完成了一个完美的闭环！

还记得你最初问我的第一个问题吗？那个 `irqreturn_t my_handler(int irq, void *dev_id)`。

你当时只看到了怎么**处理**中断，现在你终于知道了这个中断是怎么**来**的：

1. **原厂 BSP**：写好 `.dtsi`，定义好中断控制器（物业保安室）。
    
2. **你（设备树配置）**：写好 `.dts`，填好报警表格 `interrupts = <9 0>;`。
    
3. **你（驱动代码）**：在 `probe` 里用 `platform_get_irq` 把表格换成虚拟中断号 `irq`。
    
4. **你（驱动代码）**：用 `request_irq` 把你写的 `my_handler` 函数和这个 `irq` 绑定起来。
    
5. **硬件触发**：引脚电平变化 $\rightarrow$ 触发真正的中断 $\rightarrow$ 内核查表 $\rightarrow$ 执行你的 `my_handler`。
