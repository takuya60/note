# XH-202603 面向太空智算的多模态遥感大模型应用探索分析

## 1. 赛题

该赛题要求设计一个适合卫星平台受限算力部署的多模态遥感大模型系统，让模型能通过自然语言指令完成遥感图像描述、目标检测、目标计数、场景分类、语义分割、变化检测等任务，并考虑星载环境下的轻量化、可靠性和容错能力。

简单说，它不是让你从零训练一个大模型，而是让你基于已有开源多模态模型，做一个更适合遥感图像、受限算力和太空环境的系统。

## 3. 赛题核心痛点

1. **遥感任务多样**：同一系统要处理图像描述、视觉问答、目标检测、计数、分割、变化检测等任务。
2. **星载算力受限**：模型不能只追求大参数和高精度，还要考虑模型大小、显存、推理速度。
3. **泛化能力要求高**：卫星在轨任务场景变化大，不能完全依赖大量标注样本。
4. **国产 AI 芯片适配**：决赛可能需要在昇腾、天数智芯等设备上验证。
5. **空间环境可靠性**：题目提到可从单粒子翻转、错误校验、故障恢复等方面设计容错方案。

### 4.2 技术栈详解

#### 1. 基础多模态模型：让系统“看图并听懂问题”

多模态模型就是能同时处理图片和文字的模型。你给它一张遥感图，再问“图中有几艘船”，它需要看图、理解问题，并输出答案。

你不需要从零训练这种模型，应该选一个开源模型作为底座。优先考虑：

- **Qwen2.5-VL / Qwen2-VL**：中文生态好，资料多，适合国内比赛。
- **InternVL**：视觉理解能力强，开源生态成熟。
- **MiniCPM-V**：相对轻量，适合资源有限的团队。
- **LLaVA 系列**：经典视觉语言模型，教程多，但中文和遥感适配可能不如 Qwen 系列方便。

对于没有经验的团队，建议优先尝试：

> **MiniCPM-V 或 Qwen2-VL 小参数版本**

原因是资料相对多，容易跑通推理和微调。

#### 2. 遥感视觉模型：补足大模型不擅长的细粒度视觉任务

通用多模态模型擅长描述和问答，但不一定擅长精准检测、分割和变化检测。因此可以接入专门模型：

- **YOLO**：目标检测模型，适合找飞机、船、车辆、建筑等目标，并画出检测框。
- **DETR / DINO**：也是目标检测模型，偏研究型。
- **SAM / SAM2**：分割模型，可以把某个物体或区域分割出来。
- **RemoteCLIP / CLIP-RS**：遥感图像和文本对齐模型，适合做遥感图文检索、场景匹配。
- **GeoChat**：偏遥感视觉语言模型，可作为参考方向。

简单理解：

> 多模态大模型负责“理解用户想干什么”，专用视觉模型负责“把具体视觉任务做准”。

#### 3. PyTorch、Transformers、PEFT：训练和微调用

- **PyTorch**：深度学习基础框架，负责模型训练和推理。
- **Transformers**：Hugging Face 的模型库，很多开源大模型都用它加载。
- **PEFT**：参数高效微调库，LoRA / QLoRA 通常通过它实现。
- **LLaMA-Factory / XTuner**：更高级的微调工具，可以减少你自己写训练代码的工作量。

没有经验时，不建议一开始自己从零写训练脚本。建议先用 LLaMA-Factory 或模型官方微调脚本跑通一小批数据。

#### 4. LoRA / QLoRA：低成本训练的关键

从零训练大模型需要很多显卡，不现实。LoRA / QLoRA 的思路是：

- 原始大模型大部分参数不动。
- 只训练很小一部分新增参数。
- 用较少显存让模型学会遥感任务。

大致硬件判断：

| 显卡条件 | 能做什么 |
|---|---|
| 无独显 / 核显 | 不建议训练，只能写代码、处理数据、做 API 或小模型 CPU 推理 |
| 6GB-8GB 显存 | 可以尝试极小模型或只做推理，训练很吃力 |
| 12GB 显存 | 可尝试 2B-3B 小模型 QLoRA，batch size 要很小 |
| 16GB 显存 | 可以做小规模 LoRA / QLoRA 实验 |
| 24GB 显存 | 比较理想，可做 2B-7B 级别轻量微调 |
| 多卡服务器 | 可做更完整模型对比和较大规模训练 |

#### 5. 数据处理工具：把遥感数据变成模型能吃的格式

遥感数据通常不是普通图片那么简单，可能有大图、多时相、标注文件等。

- **Pillow**：打开、保存、缩放普通图片。
- **OpenCV**：图像处理、画框、切图、可视化。
- **rasterio**：处理 GeoTIFF 等遥感专业格式。
- **Albumentations**：做图像增强，例如旋转、裁剪、亮度变化。
- **pandas**：整理标注表格和训练样本。

初期可以先避开复杂 GeoTIFF，优先使用开源数据集里已经整理好的 png/jpg 图片。

#### 6. 模型压缩与部署：回应“太空智算”的核心

这个题最重要的评分之一是“资源效率与星载适配性 40 分”。因此只做大模型问答不够，必须证明模型能变小、变快、少占显存。

可做的压缩手段：

- **INT8 / INT4 量化**：把模型权重从高精度变成低精度，减少显存和存储。
- **剪枝**：去掉不重要的参数或模块。
- **蒸馏**：用大模型教小模型，让小模型接近大模型效果。
- **ONNX 导出**：把模型转成更容易部署的格式。

学生团队最现实的是：

> 先做 LoRA 微调，再做 INT8 / INT4 量化，对比量化前后效果、显存和速度。

#### 7. Gradio / Streamlit：做演示界面

比赛需要展示原型系统。Gradio 和 Streamlit 可以快速做网页 demo。

建议界面包含：

1. 上传遥感图像。
2. 输入自然语言指令。
3. 选择任务类型或由系统自动识别任务。
4. 展示回答文本。
5. 展示检测框、分割区域或变化检测叠图。
6. 显示模型大小、显存、推理时间。

## 5. 推荐系统架构

```text
遥感图像 + 自然语言指令
  ↓
图像预处理：裁剪、归一化、多尺度切片
  ↓
任务路由器：判断是描述 / 问答 / 检测 / 计数 / 分割 / 变化检测
  ↓
多模态遥感大模型主干：理解图像和问题，生成高层回答
  ↓
任务插件：检测模型、分割模型、变化检测模型、计数模块
  ↓
轻量化推理引擎：量化、缓存、批处理、端侧部署
  ↓
可靠性模块：结果一致性校验、异常检测、重试/回退
  ↓
自然语言答案 + 图像标注结果 + 资源消耗报告
```

## 6. 推荐技术路线

### 6.1 总体推荐路线

不建议做“从零训练遥感大模型”。更现实的路线是：

> **开源轻量 VLM + 遥感指令微调 + 专用视觉任务插件 + 量化压缩 + 星载容错实验**

这条路线既能体现大模型，又不会把工作量全部压在训练上。

### 6.2 第一阶段：先跑通一个最小可用 demo

目标：让系统能看一张遥感图并回答一个问题。

步骤：

1. 选择一个开源多模态模型，例如 MiniCPM-V 或 Qwen2-VL 小模型。
2. 下载少量遥感样例图片。
3. 跑通模型推理。
4. 用 Gradio 做一个最小界面：上传图片 + 输入问题 + 输出答案。
5. 记录一次推理的时间和显存占用。

这一阶段不要急着训练，先保证环境能跑通。

产出：

- 一个可演示的遥感图像问答 demo。
- 一份环境安装说明。
- 一组推理结果截图。

### 6.3 第二阶段：整理遥感指令数据

目标：把开源数据集变成“图像 + 指令 + 答案”的格式。

可以构造几类任务：

| 任务类型 | 输入 | 输出 |
|---|---|---|
| 图像描述 | 一张遥感图 | “图中为港口区域，可见多艘船只和码头设施。” |
| 视觉问答 | 图 + 问题“有几艘船？” | “图中约有 5 艘船。” |
| 目标定位 | 图 + “找出所有飞机” | 检测框坐标 + 文本说明 |
| 变化检测 | 前后两张图 + “发生了什么变化？” | “新增了建筑区域，道路扩展明显。” |
| 场景分类 | 图 + “这是什么场景？” | “机场 / 港口 / 农田 / 城市建筑区”等 |

建议先做 500-2000 条小规模指令数据，不要一开始追求大而全。

数据格式建议：

```json
{
  "image": "images/example_001.png",
  "instruction": "图像中有几艘船？",
  "answer": "图像中共有 5 艘船。",
  "task_type": "counting"
}
```

### 6.4 第三阶段：做 LoRA / QLoRA 微调

目标：让通用多模态模型更懂遥感图像。

步骤：

1. 选择小参数模型。
2. 用整理好的指令数据做 LoRA 或 QLoRA 微调。
3. 训练时只训练 LoRA 参数，不动大模型主体。
4. 保存 LoRA 权重。
5. 对比微调前和微调后的回答质量。

对比示例：

| 问题 | 微调前 | 微调后 |
|---|---|---|
| 图中主要是什么场景？ | “这是一张城市图片。” | “这是港口遥感图像，可见码头、船只和集装箱堆场。” |
| 图中是否有飞机？ | “可能有车辆。” | “图中机场跑道附近可见 3 架飞机。” |

如果没有合适显卡，可以先跳过训练，把微调作为后续增强，把重点放在任务插件、量化和容错上。

### 6.5 第四阶段：加入专用任务插件

目标：让系统不只是“说”，还可以“画框、分割、检测变化”。

建议按优先级做：

1. **目标检测插件**：用 YOLO 检测飞机、船、车辆等。
2. **目标计数插件**：检测后统计数量。
3. **分割插件**：用 SAM 或遥感分割模型分割建筑、水体、道路等。
4. **变化检测插件**：输入前后两张图，输出变化区域。

插件的作用是：

- 用户问“有几艘船？” → 系统调用检测插件。
- 用户问“把建筑区域标出来” → 系统调用分割插件。
- 用户问“洪水是否消退？” → 系统调用变化检测插件。

这可以包装成“自然语言驱动的遥感任务路由”。

### 6.6 第五阶段：做模型量化和资源评估

目标：回应评分中的“资源效率与星载适配性”。

至少做三组对比：

| 版本 | 模型大小 | 显存占用 | 单张图推理时间 | 任务准确率 |
|---|---:|---:|---:|---:|
| 原始 FP16 | 例如 8GB | 例如 12GB | 例如 3.2s | 例如 80% |
| INT8 量化 | 例如 4GB | 例如 7GB | 例如 2.1s | 例如 78% |
| INT4 量化 | 例如 2.5GB | 例如 5GB | 例如 1.6s | 例如 74% |

评审会很关注这个表，因为它直接对应 40 分的资源效率。

### 6.7 第六阶段：做星载可靠性与容错实验

目标：体现“太空智算”特色。

可以模拟三类问题：

1. **输入扰动**：图片加入噪声、模糊、亮度变化，观察结果是否稳定。
2. **模型扰动**：随机扰动少量权重或中间特征，模拟单粒子翻转影响。
3. **输出异常**：模型置信度低或多次回答不一致时，触发重试或调用备用模型。

可设计容错策略：

- 多次推理一致性投票。
- 检测结果置信度阈值过滤。
- 图像质量检测。
- 异常输出回退到轻量专用模型。
- 关键任务双模型交叉验证。

这部分不一定要非常复杂，但一定要有实验结果和图表。

### 6.8 第七阶段：做完整演示系统和报告

最终系统建议包括：

1. 图像上传。
2. 自然语言输入。
3. 自动判断任务类型。
4. 调用 VLM 或任务插件。
5. 输出文本答案。
6. 输出检测框 / 分割图 / 变化图。
7. 显示推理时间、显存、模型大小。
8. 显示量化版本对比。
9. 展示容错实验结果。

最终报告要围绕三个评分点写：

- 核心任务性能。
- 资源效率与星载适配性。
- 创新性与应用价值。

## 7. 推荐选型方案

建议采用组合方案：

> **轻量化遥感 VLM + 任务路由插件 + 星载可靠性验证**

具体做法：

1. 主干模型选择一个参数量较小、可 LoRA 微调的视觉语言模型。
2. 用开源遥感数据做指令微调，使其具备遥感问答和描述能力。
3. 对检测、分割、变化检测等结构化任务，引入轻量专用模型作为插件。
4. 统一通过自然语言指令接口调用。
5. 做量化部署测试，输出模型大小、显存、推理时延。
6. 额外加入“星载容错实验”，形成差异化创新点。

## 8. 可做创新点

1. **遥感任务路由式多模态模型**  
   根据自然语言指令自动选择图像描述、检测、分割、变化检测等子任务。

2. **星载约束下的轻量化推理方案**  
   对比 FP16、INT8、INT4 下的精度、速度、显存和模型大小。

3. **遥感大图切片与多尺度推理**  
   面向高分辨率遥感图像，设计切片、重叠合并和多尺度结果融合。

4. **星载可靠性与容错机制**  
   模拟单粒子翻转、图像噪声、模型输出异常，设计置信度校验和重试机制。

5. **少样本遥感指令微调**  
   证明在少量场景数据下也能适配新任务。

6. **国产 AI 芯片部署适配报告**  
   即使没有真实芯片，也可以提前设计 ONNX/MindSpore/Ascend 迁移路径；若能实际跑通则更强。

## 9. 数据方案

| 数据集 | 用途 |
|---|---|
| VRSBench | 遥感视觉问答、综合理解 |
| MME Real RS | 遥感多模态评测 |
| XLRS-bench | 跨语言或大规模遥感理解评测 |
| LEVIR-CC | 遥感变化描述 |
| DOTA / DIOR / NWPU VHR-10 | 遥感目标检测，可选 |
| LoveDA / Potsdam / Vaihingen | 遥感语义分割，可选 |

建议从 VRSBench 和 LEVIR-CC 入手，因为它们更贴合多模态问答和变化描述。

## 10. 评测指标建议

| 任务 | 指标 |
|---|---|
| 图像描述 | BLEU、ROUGE、CIDEr、人工评分 |
| 遥感问答 | Accuracy、F1 |
| 目标检测 | mAP、Precision、Recall |
| 目标计数 | MAE、RMSE、准确率 |
| 语义分割 | mIoU、Pixel Accuracy |
| 变化检测 | F1、IoU、变化描述质量 |
| 星载适配 | 参数量、模型大小、显存峰值、推理时延、吞吐量 |
| 可靠性 | 噪声扰动下性能下降率、故障恢复成功率、异常输出拦截率 |

## 11. 可行性分析

| 维度 | 评价 |
|---|---|
| 技术可行性 | 中等偏高。若以开源 VLM 微调 + 专用模型插件实现，能做出完整系统。 |
| 工程难度 | 较高。涉及多模态模型、遥感数据、多任务评测、模型压缩和部署。 |
| 数据难度 | 中等。赛题提供了明确开源数据集方向。 |
| 算力需求 | 中高。轻量模型 LoRA 可控，但完整训练大模型难度较大。 |
| 展示效果 | 中等偏强。可通过遥感图像问答、检测框、变化检测叠图展示。 |
| 创新空间 | 较强，尤其是星载轻量化和容错设计。 |
| 最大风险 | 竞争可能偏硬核，评审非常看重真实性能和资源效率；普通 API demo 不够。 |

## 12. 推荐原型功能清单

1. 上传遥感图像。
2. 输入自然语言指令。
3. 支持图像描述、问答、计数、检测、分割、变化检测中的至少 3-4 类任务。
4. 输出自然语言结果和图像叠加可视化。
5. 显示模型推理时间、显存占用、模型大小。
6. 提供量化前后对比。
7. 提供星载故障注入和容错演示。
8. 提供一键运行脚本和完整技术报告。

## 13. 推荐项目命名与包装方向

可包装为：

- **“星瞳”：面向太空智算的轻量化多模态遥感大模型系统**
- **“Orbit-VLM”：星载受限算力下的遥感视觉语言模型与容错推理框架**
- **“天算遥感智能体”：自然语言驱动的星载遥感解译系统**

包装重点：

1. 不是普通遥感识别，而是“星载受限算力 + 多模态指令理解”。
2. 不是只追求精度，而是精度、速度、显存、可靠性的综合权衡。
3. 强调国产 AI 芯片迁移潜力。
4. 强调应急救灾、生态监测等高时效场景。

## 14. 适合什么团队选择

适合：

- 团队有计算机视觉、多模态大模型、深度学习训练经验，或者愿意集中学习。
- 有 GPU 资源，至少能做 LoRA 微调或轻量模型训练。
- 有同学熟悉遥感图像、目标检测、分割或模型压缩。
- 愿意做较硬核的实验和指标对比。

不太适合：

- 团队只熟悉大模型 API 调用，不熟悉训练和评测。
- 缺少 GPU 或无法稳定跑深度学习实验。
- 希望短时间做出偏产品化 demo，而不是算法模型作品。

## 15. 新手学习顺序建议

如果你们之前没做过遥感和多模态，建议按这个顺序学：

1. Python 深度学习基础：PyTorch 张量、模型加载、GPU 使用。
2. 图像处理基础：Pillow、OpenCV、图片裁剪和画框。
3. 先跑通一个开源 VLM 的推理。
4. 学会 Hugging Face Transformers 加载模型。
5. 学 LoRA / QLoRA 微调基本概念。
6. 整理一个小型遥感指令数据集。
7. 做一次小规模微调。
8. 学 YOLO 检测并接入系统。
9. 做量化和推理速度测试。
10. 最后再做星载容错和报告包装。

## 16. 综合判断

这是剩余三个题目中技术硬度最高、专业性最强的方向之一。它的优点是航天背景强、技术含金量高、评分指标明确；缺点是门槛高、训练和部署压力大，且决赛会考验国产 AI 芯片适配和闭源数据泛化。

如果团队有较强深度学习和计算机视觉能力，并且有一定算力资源，该题有较高获奖潜力；如果团队主要优势是大模型应用开发和前端展示，则不建议优先选择。
