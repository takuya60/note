# XH-202631 面向超长程复杂任务的动态异构群体智能架构与深度协同推理技术分析

## 1. 赛题一句话理解

该赛题要求构建一个能够完成超长程复杂任务的多智能体系统，不是简单地把多个 Agent 串起来，而是要解决长上下文记忆保持、动态任务编排、异构智能体协作、低冗余通信、端边云调度和故障自恢复等底层架构问题，并能在多个产业场景中无人工干预完成闭环任务。

简单说，这个题不是做一个普通聊天机器人，而是做一个“能自己拆任务、分配角色、调用工具、检查结果、失败后恢复”的智能体协作系统。

## 2. 赛题关键信息

| 项目   | 内容                                            |
| ---- | --------------------------------------------- |
| 题目编号 | XH-202631                                     |
| 核心场景 | 超长程复杂任务、多智能体协同、AGI、数字劳动力、端边云协同、自动化闭环交付        |
| 关键能力 | 长程上下文连续性、动态异构拓扑、低熵通信、端边云调度、异常/需求变更/节点失效下的自主恢复 |
| 交付要求 | 材料文档 + 可运行系统；完整演示无人工干预下的多智能体长程协作闭环            |
| 评分重点 | 作品完整性 40%，应用创新性 25%，技术创新性 20%，系统性能与效率 15%     |

## 3. 赛题核心痛点

1. **单体智能体长程任务容易记忆坍缩**：任务步骤多、上下文长，模型容易忘记目标、约束和中间结论。
2. **传统多智能体通信冗余严重**：全连接群聊式 Agent 容易 token 爆炸、噪声传播、决策混乱。
3. **任务拓扑不应固定**：不同任务需要不同角色、不同协作方式，不能用固定流水线解决所有问题。
4. **需要端边云异构调度**：不同子任务要根据实时性、隐私性、复杂度选择执行位置。
5. **必须能应对异常**：需求变更、工具失败、节点失效时，系统要能自主恢复。
6. **评测要求抽象且开放**：没有明确数据集，必须自己设计能体现技术深度和演示效果的场景。

## 4. 推荐技术栈

### 4.1 技术栈总表

| 模块 | 推荐技术 | 说明 |
|---|---|---|
| Agent 框架 | LangGraph、AutoGen、CrewAI、OpenAI Swarm 风格框架、自研编排器 | 更推荐基于 LangGraph 或自研轻量状态机，便于展示动态拓扑 |
| 大模型 | Qwen、DeepSeek、GLM、Claude/OpenAI API 可选 | 需要支持复杂规划、代码生成、总结和反思 |
| 任务编排 | 有向图 DAG、状态机、黑板系统、事件总线 | 用于动态路由和任务状态管理 |
| 记忆系统 | SQLite/PostgreSQL + 向量库 FAISS/Chroma + 摘要树 | 支持长期记忆、任务记忆、检查点 |
| 工具调用 | Python 沙箱、浏览器自动化、文件操作、API 调用、代码执行器 | 用于完成真实任务闭环 |
| 通信协议 | JSON Schema、Pydantic、Protobuf 可选 | 结构化消息降低 token 冗余 |
| 可视化 | React Flow、D3.js、ECharts、Graphviz | 展示动态拓扑、消息流、任务进度和回滚路径 |
| 端边云模拟 | 本地进程/容器模拟终端、边缘和云端 | 不一定要真实硬件，重点是调度策略和约束建模 |
| 容错机制 | 检查点、重试、投票、回滚、替代 Agent 路由 | 展示鲁棒性 |

### 4.2 技术栈详解

#### 1. 什么是 Agent

Agent 可以理解为“带有目标、记忆和工具使用能力的 AI 角色”。

普通大模型聊天是：

```text
用户提问 → 模型回答
```

Agent 是：

```text
用户给目标 → Agent 拆解任务 → 调用工具 → 检查结果 → 继续下一步 → 最终交付
```

例如一个代码 Agent 可以：

1. 理解需求。
2. 查看项目文件。
3. 修改代码。
4. 运行测试。
5. 根据报错修复。
6. 输出总结。

这个赛题要做的不是一个 Agent，而是一群 Agent 协作。

#### 2. 多智能体系统：多个角色分工合作

多智能体系统可以有不同角色：

| Agent 角色 | 作用 |
|---|---|
| Planner 规划 Agent | 把大任务拆成小任务 |
| Executor 执行 Agent | 调用工具完成具体步骤 |
| Coder 代码 Agent | 写代码、改代码 |
| Researcher 研究 Agent | 搜集资料、整理信息 |
| Reviewer 评审 Agent | 检查结果是否符合要求 |
| Memory 记忆 Agent | 管理长期目标、关键事实、历史决策 |
| Router 路由 Agent | 决定哪个任务交给哪个 Agent |
| Recovery 恢复 Agent | 出错后判断怎么回滚、重试或换人 |

普通做法是固定流水线：Planner → Executor → Reviewer。  
这个赛题要求更高级：任务不同，参与 Agent 和协作关系也要动态变化。

#### 3. LangGraph：推荐的 Agent 编排框架

LangGraph 可以把智能体流程表示成“图”。

- 图里的节点可以是一个 Agent、一个函数、一个工具。
- 边表示下一步去哪里。
- 状态可以在节点之间传递。
- 可以加入条件判断、循环、失败恢复。

它比普通 LangChain 更适合这个题，因为赛题强调“动态拓扑”“任务图”“长程状态”。

如果你们没有经验，建议优先用：

> **LangGraph + Python + FastAPI + React Flow**

这套技术栈比较适合做“可视化多智能体任务图”。

#### 4. AutoGen / CrewAI：更容易上手，但要小心同质化

- **AutoGen**：适合多 Agent 对话协作，资料多，上手较快。
- **CrewAI**：角色、任务、工具概念清楚，适合快速搭原型。

但这两个框架容易做成普通多 Agent demo。如果使用它们，必须加入自己的创新：

- 动态任务图。
- 结构化通信协议。
- 记忆与检查点。
- 异常注入恢复。
- token 消耗统计。

否则评审可能认为只是套框架。

#### 5. 大模型：系统的大脑

大模型用于：

- 理解用户目标。
- 拆解任务。
- 生成代码或报告。
- 总结中间结果。
- 判断结果是否合格。
- 决定下一步行动。

模型可以用 API，也可以用本地开源模型。

| 方案 | 优点 | 缺点 |
|---|---|---|
| API 模型 | 效果强、部署简单、适合演示 | 成本、网络、稳定性、数据隐私问题 |
| 本地开源模型 | 可控、可包装端侧/边缘部署 | 需要显卡，效果可能弱 |
| 混合方案 | 云端用强模型，本地用小模型 | 架构复杂，但最贴合端边云 |

如果为了比赛稳定，建议：

> 原型阶段使用 API 或较强开源模型；系统设计中体现端边云混合调度。

#### 6. DAG：任务图，是这个题的核心表达方式

DAG 是有向无环图。可以理解成任务依赖关系图。

例如用户说：

> 帮我做一个市场调研报告，并生成 PPT 大纲。

系统可以拆成：

```text
理解需求
  ↓
搜集资料 ──→ 竞品分析 ──→ 总结机会点
  ↓                         ↓
用户画像分析 ─────────────→ 生成报告
                            ↓
                         生成 PPT 大纲
```

每个节点都是一个子任务。节点之间有依赖关系。这个图不是固定写死，而是模型根据任务动态生成。

#### 7. 状态机：保证长任务不会乱

长程任务最怕“跑着跑着忘了目标”。状态机用于记录当前任务到底进行到哪一步。

常见状态：

| 状态 | 含义 |
|---|---|
| pending | 等待执行 |
| running | 正在执行 |
| completed | 已完成 |
| failed | 执行失败 |
| blocked | 被其他任务阻塞 |
| retrying | 正在重试 |
| revised | 因需求变更被修改 |

每个子任务都有状态，系统就不会只靠大模型上下文记忆。

#### 8. 记忆系统：解决长上下文和任务遗忘

记忆系统不是简单地把聊天记录都塞给模型。更好的做法是分层记忆：

| 记忆类型 | 保存内容 | 用途 |
|---|---|---|
| 全局目标记忆 | 用户最终目标、硬约束、交付物要求 | 防止偏离目标 |
| 任务状态记忆 | 每个子任务完成到哪一步 | 恢复和继续执行 |
| 证据记忆 | 文件路径、实验结果、资料来源 | 支持可追溯 |
| 决策记忆 | 为什么选择某个方案 | 便于答辩解释 |
| 检查点 | 阶段性产物快照 | 出错后回滚 |

可以用：

- SQLite 保存结构化任务状态。
- 向量库保存可检索资料和历史摘要。
- 文件系统保存中间产物和检查点。

#### 9. 向量库：用于语义检索，不是必须但很有用

向量库可以把长文本、资料、历史记录变成可检索的向量。

常用：

- FAISS：轻量，本地可用。
- Chroma：上手简单。
- Milvus：更工程化，但重一些。

在这个题中，向量库可用于：

- 检索历史任务经验。
- 检索用户目标和约束。
- 检索调研资料。
- 检索代码文件摘要。

但要注意：任务状态不要只放向量库，应该放 SQLite/PostgreSQL 这种结构化数据库。

#### 10. JSON Schema / Pydantic：让 Agent 不要乱说

普通 Agent 用自然语言聊天，容易冗余和不稳定。结构化通信可以要求每条消息都按固定格式输出。

例如：

```json
{
  "message_type": "task_result",
  "task_id": "T12",
  "status": "completed",
  "summary": "已完成登录功能测试",
  "evidence": ["tests/auth.test.ts"],
  "next_action": "run_all_tests"
}
```

Pydantic 可以在 Python 中校验这个 JSON 是否合格。这样可以减少：

- 废话。
- 无效消息。
- 角色之间互相污染。
- token 浪费。

这就是“低熵通信”的工程实现方式。

#### 11. 工具调用：让 Agent 真的做事

Agent 必须能调用工具，否则只是聊天。

可以接入的工具：

- 文件读写工具。
- Python 代码执行工具。
- Shell 命令工具。
- 浏览器自动化工具。
- API 请求工具。
- 文档生成工具。
- 测试运行工具。

如果选择“自动化软件工程任务”作为演示场景，工具调用非常关键。

#### 12. React Flow / D3：把任务图展示出来

这个赛题很抽象，必须可视化，否则评审很难理解你做了什么。

建议展示：

- 当前任务图。
- 每个节点状态。
- 哪些 Agent 正在执行。
- Agent 之间传了哪些结构化消息。
- token 消耗。
- 出错后如何重试或改路由。
- 端、边、云分别执行了哪些任务。

React Flow 很适合展示节点和连线。

#### 13. 端边云模拟：不一定要真实硬件

题目提到端-边-云异构资源调度。学生团队不一定有真实手机、边缘服务器和云集群，可以用模拟方式：

- 端侧：本地小模型 / 本地函数，假设算力低、隐私高。
- 边缘：本地另一个进程，假设中等算力。
- 云端：API 强模型，假设算力强但成本高。

系统根据任务属性决定放在哪里执行。

例如：

| 子任务 | 隐私等级 | 算力需求 | 推荐位置 |
|---|---|---|---|
| 读取本地用户文件 | 高 | 低 | 端侧 |
| 代码生成 | 中 | 高 | 云端 |
| 格式检查 | 低 | 低 | 端侧 |
| 汇总多个结果 | 中 | 中 | 边缘 |

#### 14. 容错机制：评审会很关注

赛题明确要求系统能面对异常、需求变更、节点失效。

必须设计：

- 重试机制。
- 超时检测。
- Agent 替换。
- 检查点回滚。
- 任务图重构。
- 失败原因记录。

演示时不要只展示成功，还要故意让一个节点失败，然后展示系统如何恢复。

## 5. 推荐系统架构

```text
用户高层意图
  ↓
任务理解器：目标、约束、交付物、风险识别
  ↓
任务图生成器：将复杂任务拆成动态 DAG
  ↓
角色池：规划 Agent / 执行 Agent / 评审 Agent / 工具 Agent / 记忆 Agent / 调度 Agent
  ↓
动态路由器：根据任务状态选择参与 Agent 和通信路径
  ↓
低熵通信协议：只传结构化摘要、证据、决策，不传完整聊天记录
  ↓
分布式记忆：全局目标、子任务状态、关键证据、检查点
  ↓
端边云调度器：根据隐私、算力、时延选择执行位置
  ↓
执行与反馈：工具调用、代码运行、文件生成、API 调用
  ↓
自检与恢复：异常检测、节点替换、回滚、再规划
  ↓
最终交付物 + 全链路推理轨迹 + 动态拓扑可视化
```

## 6. 推荐技术路线

### 6.1 总体推荐路线

最推荐路线是：

> **动态任务图 + 结构化低熵通信 + 分层记忆检查点 + 异常恢复 + 两个长程任务演示**

不要一开始就追求做一个“万能 AGI 系统”。比赛需要的是一个有明确技术创新点、可运行、可评测、可演示的系统。

### 6.2 第一阶段：先做一个单任务 Agent 闭环

目标：让一个 Agent 能独立完成简单任务。

建议从软件工程任务开始，因为它容易验证。

示例任务：

> 为一个简单 Todo 应用增加任务搜索功能，并补充测试。

系统要能：

1. 读取需求。
2. 查看项目文件。
3. 找到要改的文件。
4. 修改代码。
5. 运行测试。
6. 如果报错，继续修复。
7. 输出完成报告。

这一阶段不需要多 Agent，先保证“AI 能真的调用工具做事”。

### 6.3 第二阶段：拆成多个角色 Agent

目标：从单 Agent 变成多 Agent 协作。

可以设计 4 个基础角色：

| Agent | 职责 |
|---|---|
| Planner | 拆解任务，生成任务图 |
| Executor | 执行具体任务，调用工具 |
| Reviewer | 检查结果和质量 |
| Memory Manager | 保存任务状态、目标和证据 |

初始流程可以是：

```text
用户任务
  ↓
Planner 拆任务
  ↓
Executor 执行
  ↓
Reviewer 检查
  ↓
Memory Manager 记录结果
```

虽然这是固定流程，但它是基础。后面再升级成动态拓扑。

### 6.4 第三阶段：引入任务图

目标：让任务不是线性流程，而是一个图。

每个任务节点至少包含：

```json
{
  "task_id": "T3",
  "goal": "为搜索功能补充单元测试",
  "input": ["src/todo.ts", "tests/todo.test.ts"],
  "output": ["updated tests"],
  "depends_on": ["T1", "T2"],
  "required_capability": ["code", "test"],
  "status": "pending",
  "failure_policy": "retry_then_replan"
}
```

任务图的价值：

- 可以并行执行无依赖任务。
- 可以看到哪个任务阻塞了整体进度。
- 失败时只回滚相关节点，不用全局重来。
- 可视化效果强。

### 6.5 第四阶段：做动态路由

目标：不再固定某个 Agent 做某个任务，而是根据任务需要选择 Agent。

每个 Agent 注册自己的能力：

```json
{
  "agent_name": "code_agent",
  "capabilities": ["code", "debug", "test"],
  "cost_level": "medium",
  "reliability": 0.86,
  "runtime": "cloud"
}
```

路由器根据子任务需求选择：

```text
如果任务需要 code + test → 选择 code_agent
如果任务需要 research → 选择 research_agent
如果任务失败两次 → 切换到 backup_agent
如果任务隐私等级高 → 选择 local_agent
```

这就是“动态异构拓扑”的核心。

### 6.6 第五阶段：设计低熵通信协议

目标：减少 Agent 之间无意义聊天。

不要让 Agent 用长篇自然语言互相聊天，而是统一使用结构化消息。

消息类型可以包括：

| message_type | 用途 |
|---|---|
| task_plan | 任务计划 |
| task_result | 任务结果 |
| risk_report | 风险或问题报告 |
| review_feedback | 评审意见 |
| memory_update | 记忆更新 |
| recovery_request | 恢复请求 |
| routing_decision | 路由决策 |

结构化消息示例：

```json
{
  "sender": "review_agent",
  "receiver": "planner_agent",
  "message_type": "risk_report",
  "task_id": "T8",
  "summary": "登录模块缺少密码错误测试",
  "evidence": ["tests/auth.test.ts"],
  "suggested_action": "add_test_case",
  "confidence": 0.86
}
```

评测时可以对比：

| 通信方式 | token 消耗 | 无效消息比例 | 任务成功率 |
|---|---:|---:|---:|
| 普通群聊式 Agent | 高 | 高 | 中 |
| 结构化低熵通信 | 低 | 低 | 高 |

### 6.7 第六阶段：做长程记忆和检查点

目标：长任务中不丢失目标、约束和中间结论。

建议把记忆分成三类系统：

#### 结构化状态库

用 SQLite/PostgreSQL 保存：

- 用户目标。
- 子任务列表。
- 子任务状态。
- Agent 执行记录。
- 错误记录。
- 路由决策。

#### 语义检索库

用 FAISS/Chroma 保存：

- 文档摘要。
- 历史任务经验。
- 重要上下文。
- 代码文件摘要。

#### 文件检查点

保存：

- 修改前代码快照。
- 中间报告版本。
- 任务图版本。
- 工具执行日志。

这样可以证明：

> 系统不是靠模型长上下文硬撑，而是靠外部状态和记忆机制保持长程一致性。

### 6.8 第七阶段：做异常注入与恢复

目标：证明系统鲁棒。

建议设计三种演示异常：

#### 异常 1：需求变更

原始任务：

> 做一个密码登录功能。

中途注入：

> 改成验证码登录。

系统应：

1. 检测需求变更。
2. 找出受影响子任务。
3. 修改任务图。
4. 废弃或回滚相关结果。
5. 继续执行新任务。

#### 异常 2：工具失败

例如测试命令失败。

系统应：

1. 读取错误日志。
2. 判断是代码问题、环境问题还是测试问题。
3. 分配给 debug Agent。
4. 修复后重新运行。

#### 异常 3：节点失效

模拟某个 Agent 超时或返回格式错误。

系统应：

1. 标记该节点失败。
2. 切换备用 Agent。
3. 从检查点恢复上下文。
4. 继续执行。

这部分非常适合录视频，能明显区别于普通 Agent demo。

### 6.9 第八阶段：做端边云调度模拟

目标：回应荣耀赛题中“终端、边缘、云端异构资源”的要求。

可以设计一个调度分数：

```text
score = 算力需求 + 时延要求 + 隐私等级 + 当前成本
```

示例策略：

| 子任务 | 推荐位置 | 原因 |
|---|---|---|
| 用户本地文件摘要 | 端侧 | 隐私高，计算量小 |
| 大规模代码生成 | 云端 | 算力需求高 |
| 多个结果汇总 | 边缘 | 计算量中等，需要聚合 |
| 格式检查 | 端侧 | 简单、低延迟 |
| 深度方案评审 | 云端 | 需要强模型推理 |

演示时可以在可视化页面上标出每个任务节点运行在端、边还是云。

### 6.10 第九阶段：准备两个长程任务演示

赛题评分中强调多任务场景，建议至少准备两个。

#### 演示任务 1：自动化软件工程

输入：

> 为一个 Todo Web 应用增加用户登录、搜索、任务分类和测试。

展示：

- 自动拆任务。
- 多 Agent 协作改代码。
- 运行测试。
- 测试失败后自动修复。
- 输出交付报告。

#### 演示任务 2：复杂调研与方案生成

输入：

> 为一款面向大学生的 AI 学习助手设计市场分析报告和产品方案。

展示：

- 资料搜集。
- 竞品分析。
- 用户画像。
- 风险评估。
- 生成报告和 PPT 大纲。
- 中途需求变更后重构任务图。

如果你们想更贴合荣耀，也可以把第二个任务改成：

> 面向手机终端的多设备智能助手任务，例如自动整理会议资料、生成纪要、规划后续待办。

### 6.11 第十阶段：做评测和可视化

必须量化，不然容易被认为只是演示。

建议评测：

| 指标 | 怎么测 |
|---|---|
| 任务成功率 | 10 个任务中成功完成几个 |
| 平均 token 消耗 | 每个任务总消息 token 数 |
| 无效通信比例 | 没有产生决策价值的消息占比 |
| 异常恢复成功率 | 注入异常后成功恢复的比例 |
| 平均恢复时间 | 从异常发生到恢复的时间 |
| 目标遗忘次数 | 是否违反原始约束 |
| 任务图调整次数 | 动态拓扑是否真的发生变化 |

可视化页面至少展示：

1. 任务图。
2. Agent 列表和状态。
3. 消息流。
4. token 消耗。
5. 端边云分布。
6. 异常恢复过程。
7. 最终交付物。

## 7. 可做创新点

1. **动态任务图生成与重构**  
   任务图随需求变化、执行失败、节点失效动态调整。

2. **低熵结构化通信协议**  
   通过消息类型、摘要、证据、置信度减少无效 token。

3. **分布式长程记忆与检查点机制**  
   保持全局目标和中间决策不丢失，可回滚可审计。

4. **异构 Agent 能力注册与动态选择**  
   每个 Agent 有能力标签、成本、可靠性评分，调度器动态选用。

5. **端边云资源自适应调度**  
   根据隐私、时延、算力和成本自动分配推理位置。

6. **异常注入评测框架**  
   主动制造失败，证明系统不是一次性 demo，而有鲁棒性。

## 8. 评测指标建议

| 评测维度 | 指标 |
|---|---|
| 任务完成 | 成功率、完成度评分、交付物质量 |
| 长程记忆 | 目标遗忘次数、约束违反次数、中间决策召回准确率 |
| 通信效率 | token 总消耗、无效消息比例、平均消息长度 |
| 动态拓扑 | 平均参与 Agent 数、拓扑调整次数、路由命中率 |
| 鲁棒性 | 异常恢复成功率、平均恢复时间、重试次数 |
| 资源效率 | 执行时间、token 成本、端/边/云任务分布 |
| 可扩展性 | 新增 Agent 角色成本、替换模型能力 |
| 用户体验 | 任务轨迹可视化清晰度、交互复杂度 |

## 9. 可行性分析

| 维度 | 评价 |
|---|---|
| 技术可行性 | 中等。做出可运行原型可行，但做出“底层突破感”较难。 |
| 工程难度 | 高。需要智能体框架、工具调用、记忆、可视化、容错和评测。 |
| 数据难度 | 低到中。无需固定数据集，但需要自建评测任务集。 |
| 算力需求 | 中等。可主要依赖 API 或开源模型；难点不在训练而在架构。 |
| 展示效果 | 取决于设计。若动态图和异常恢复做得好，展示效果很强；否则容易像普通 Agent demo。 |
| 创新空间 | 很高。题目非常前沿，容易讲出 AGI、多智能体、数字劳动力故事。 |
| 最大风险 | 题目过于抽象，评审可能认为作品只是套壳 Agent 框架；需要用量化指标和失败恢复证明深度。 |

## 10. 推荐原型功能清单

1. 用户输入高层复杂任务。
2. 自动生成动态任务图。
3. 多类异构 Agent 注册与调度。
4. 结构化消息通信与 token 统计。
5. 长程记忆、任务状态和检查点管理。
6. 工具调用执行真实任务，例如生成代码、运行测试、生成报告。
7. 支持需求变更、工具失败、节点失效注入。
8. 自动恢复与再规划。
9. 可视化展示任务图、消息流、执行轨迹、资源消耗。
10. 至少演示两个不同类型长程任务。

## 11. 新手学习顺序建议

如果你们没有 Agent 开发经验，建议按这个顺序学：

1. 先用一个大模型 API 做普通问答。
2. 学会让模型输出固定 JSON。
3. 学会写一个简单工具调用，例如读文件、写文件、运行 Python。
4. 做一个单 Agent 自动完成小任务。
5. 学 LangGraph 或 CrewAI，理解节点、边、状态。
6. 做 Planner + Executor + Reviewer 三角色协作。
7. 把任务拆成 DAG，并保存到数据库。
8. 做结构化消息协议和 Pydantic 校验。
9. 加入任务状态、记忆和检查点。
10. 加入异常注入和恢复。
11. 做 React Flow 可视化任务图。
12. 最后做端边云调度模拟和指标评测。

## 12. 推荐项目命名与包装方向

可包装为：

- **“蜂群智核”：面向超长程任务的动态异构多智能体自治引擎**
- **“Honor-SwarmOS”：端边云协同的低熵群体智能架构**
- **“TaskWeaver-X”：可恢复、可审计、低冗余通信的多智能体执行系统**

包装重点：

1. 不是普通多 Agent 聊天，而是“动态拓扑 + 低熵通信 + 长程记忆 + 容错恢复”。
2. 不是只做任务规划，而是无人工干预闭环交付。
3. 不是只展示成功案例，还展示异常注入后的恢复能力。
4. 贴合荣耀终端生态，可强调未来手机/PC/IoT 智能体协同。

## 13. 适合什么团队选择

适合：

- 团队熟悉大模型 Agent、工具调用、后端架构和前端可视化，或者愿意集中学习。
- 有能力快速搭建复杂系统原型。
- 有同学能设计评测指标和实验对比。
- 希望挑战前沿、抽象、架构型题目。

不太适合：

- 团队只会调用单个大模型 API。
- 缺少工程架构能力和系统可视化能力。
- 希望做需求明确、评分边界清楚的题目。
- 无法投入时间设计高质量演示任务和异常注入实验。

## 14. 综合判断

这是剩余三个题目中最“智能体”和最前沿的方向，但也是最容易做虚的方向。题目给的概念非常大，如果只做一个 Planner-Coder-Reviewer 的普通多 Agent 系统，很难体现“动态异构群体智能架构与深度协同推理”。

如果团队有较强 Agent 工程能力，并且能做出动态任务图、低熵通信、长程记忆、异常恢复和可视化评测，这个题目有很高上限；如果团队经验不足，它会比看起来更难，容易最后变成空泛 PPT。
