# XH-202631 面向超长程复杂任务的动态异构群体智能架构与深度协同推理技术分析

## 1. 赛题理解

这个题要求做一个能完成超长程复杂任务的多智能体系统。它不是普通聊天机器人，也不是简单模仿 Claude Code / Codex，而是要研究多个 Agent 如何动态分工、协作、记忆、通信、恢复失败，并最终完成复杂任务。

核心是“多个智能体如何稳定协同完成长任务”。

## 2. 核心难点

1. **题目抽象**：没有固定数据集或明确任务，必须自己设计场景和评测。
2. **容易做虚**：如果只是 Planner → Coder → Reviewer，会像普通 Agent demo。
3. **长程任务容易崩**：模型容易忘目标、丢上下文、重复规划。
4. **演示不稳定**：Agent 系统依赖模型输出，现场演示有波动风险。
5. **要证明架构创新**：必须有动态任务图、低熵通信、记忆、容错等机制。

## 3. 技术栈详解

| 模块       | 推荐技术                                        | 用途                              |
| -------- | ------------------------------------------- | ------------------------------- |
| Agent 框架 | LangGraph / AutoGen / CrewAI / 自研状态机        | 编排多个 Agent 的协作流程                |
| 大模型      | Qwen / DeepSeek / GLM / Claude / OpenAI API | 负责规划、推理、代码生成、总结                 |
| 任务图      | DAG / 状态机                                   | 把复杂任务拆成有依赖关系的子任务                |
| 记忆系统     | SQLite / PostgreSQL / FAISS / Chroma        | 保存目标、状态、证据、历史决策                 |
| 工具调用     | 文件读写、代码执行、浏览器、API 调用                        | 让 Agent 真正完成任务，而不是只聊天           |
| 通信协议     | JSON Schema / Pydantic                      | 让 Agent 用结构化消息交流，减少废话和 token 浪费 |
| 可视化      | React Flow / D3 / ECharts / Graphviz        | 展示任务图、消息流、Agent 状态              |
| 容错机制     | 检查点、重试、回滚、替代 Agent                          | 处理工具失败、需求变更、节点失效                |

### 3.1 Agent 框架

Agent 框架用于组织多个智能体的协作。LangGraph 更适合做状态机和任务图，适合这个题的动态拓扑和长程状态管理。AutoGen 和 CrewAI 上手更快，但容易做成普通多 Agent 聊天，需要额外设计动态任务图和结构化通信。

如果团队想稳妥，推荐用 LangGraph 或自研轻量状态机，因为你们能更清楚地展示任务节点、状态转移和失败恢复。

### 3.2 大模型

大模型负责规划、推理、代码生成、总结、反思等核心能力。可以用 Qwen、DeepSeek、GLM 等国产模型，也可以用 Claude / OpenAI API。

比赛原型阶段可以用 API 保证效果；如果要贴合端边云，可以设计为“本地小模型处理简单任务，云端强模型处理复杂任务”。

### 3.3 任务图与状态机

任务图是这个题的核心表达方式。复杂任务不能只靠聊天记录推进，而应该拆成多个子任务节点，每个节点有状态、依赖、负责人和失败策略。

状态机负责记录任务进度，例如 pending、running、completed、failed、retrying。这样系统在长任务中不容易混乱，也方便可视化和恢复。

### 3.4 记忆系统

记忆系统用于解决长任务中的遗忘问题。建议分成两类：

- 结构化记忆：用 SQLite / PostgreSQL 保存目标、任务状态、错误日志、决策记录。
- 语义记忆：用 FAISS / Chroma 保存文档摘要、历史经验、可检索上下文。

关键是证明系统不是完全依赖模型长上下文，而是有外部状态和记忆机制。

### 3.5 工具调用

Agent 必须能调用工具，否则只是聊天。可接入的工具包括：

- 文件读取和写入。
- Python / Shell 执行。
- 测试运行。
- API 请求。
- 文档生成。
- 浏览器自动化。

如果选软件工程任务作为演示，工具调用就是核心能力。

### 3.6 结构化通信

普通多 Agent 群聊会产生大量废话和 token 浪费。这个题可以用 JSON Schema / Pydantic 规范消息格式，让每条消息只包含任务 ID、结论、证据、下一步建议和置信度。

这就是“低熵通信”的工程落地方式，也是区别于普通 Agent demo 的关键。

### 3.7 可视化

题目很抽象，所以必须可视化。React Flow 很适合展示任务图，ECharts 可以展示 token 消耗、任务耗时、成功率和恢复次数。

演示时要让评委看到：任务如何拆分、哪个 Agent 正在执行、哪里失败、如何恢复、最终如何交付。

## 4. 推荐技术路线

### 阶段一：先做单 Agent 工具闭环

选一个简单软件工程任务，例如：

> 给 Todo 应用增加搜索功能并补充测试。

系统先实现：

1. 读取需求。
2. 查看文件。
3. 修改代码。
4. 运行测试。
5. 根据报错修复。
6. 输出结果。

目标：先证明 AI 能调用工具完成真实任务。

### 阶段二：拆成多个 Agent

设计基础角色：

| Agent | 职责 |
|---|---|
| Planner | 拆解任务 |
| Executor | 执行任务 |
| Reviewer | 检查结果 |
| Memory Manager | 保存目标和状态 |

初期可以先固定流程，后面再做动态路由。

### 阶段三：引入动态任务图

每个任务节点包含：

```json
{
  "task_id": "T3",
  "goal": "补充搜索功能测试",
  "depends_on": ["T1", "T2"],
  "required_capability": ["code", "test"],
  "status": "pending",
  "failure_policy": "retry_then_replan"
}
```

好处：

- 可以看到任务依赖。
- 可以并行执行无依赖任务。
- 失败时只重做相关节点。
- 可视化效果强。

### 阶段四：设计低熵通信

不要让 Agent 自由聊天，统一用 JSON 消息：

```json
{
  "sender": "review_agent",
  "receiver": "planner_agent",
  "message_type": "risk_report",
  "task_id": "T8",
  "summary": "测试缺少边界情况",
  "suggested_action": "add_test_case",
  "confidence": 0.86
}
```

可以对比：

- 普通群聊式 Agent：token 多、噪声大。
- 结构化通信：token 少、流程清楚、易复现。

### 阶段五：加入记忆和检查点

至少保存：

- 用户最终目标。
- 子任务状态。
- 已完成结果。
- 错误日志。
- 关键决策。
- 文件快照。

这样可以证明系统不是靠模型长上下文硬撑，而是有外部状态管理。

### 阶段六：异常注入与恢复

必须演示失败恢复，否则不像赛题要求的“高鲁棒性”。

建议演示三类异常：

1. **需求变更**：中途把登录方式从密码改成验证码。
2. **工具失败**：测试失败后自动定位和修复。
3. **Agent 失效**：某个 Agent 超时，系统切换备用 Agent。

### 阶段七：准备两个演示任务

建议至少两个跨领域任务：

1. **软件工程任务**：自动修改代码、测试、修复。
2. **调研报告任务**：自动拆解、搜集资料、生成分析报告和 PPT 大纲。

这样能体现系统不是只能做代码，而是通用多智能体平台。

## 5. 可做创新点

1. 动态任务图生成与重构。
2. 结构化低熵通信协议。
3. 长程记忆与检查点恢复。
4. Agent 能力注册与动态路由。
5. 异常注入和自恢复评测。
6. 端边云调度模拟：隐私高的任务端侧执行，复杂推理云端执行。

## 6. 可行性判断

| 维度 | 判断 |
|---|---|
| 技术难度 | 中高 |
| 算力需求 | 中等，可主要调用 API |
| 展示效果 | 取决于可视化和稳定性 |
| 获奖上限 | 高 |
| 主要风险 | 抽象、容易做虚、演示不稳定、评测难设计 |

## 7. 适合的团队

适合：

- 熟悉大模型 Agent、后端架构、工具调用。
- 有能力做可视化任务图。
- 愿意设计评测指标和异常恢复实验。
- 想冲智能体前沿上限。

不适合：

- 只会单轮调用大模型 API。
- 工程架构能力弱。
- 希望需求明确、评分边界清楚。

## 8. 结论

这个题上限高，但风险也高。它最贴近通用多智能体架构，但必须避免做成普通 Agent demo。只有当团队能做出“动态任务图 + 低熵通信 + 记忆检查点 + 异常恢复 + 可视化评测”时，才值得选。
