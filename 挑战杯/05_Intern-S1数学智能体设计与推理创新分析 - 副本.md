# XH-202627 基于 Intern-S1 的数学智能体设计与推理创新分析

## 1. 赛题一句话理解

该赛题要求基于上海人工智能实验室提供的 **Intern-S1 模型 API**，构建一个能自动求解多类型数学问题、输出结构化答案、解释推理过程，并在决赛阶段扩展为多智能体协作的数学智能体系统。

简单说，这个题不是让你训练数学大模型，而是让你围绕一个指定模型 API，设计更好的“数学解题智能体”：会读题、分类、规划、调用工具、校验答案、解释过程，并用 JSON 输出可评测结果。

## 3. 赛题核心痛点

1. **正确率是绝对核心**：答案正确性占 60 分，远高于系统设计和展示。
2. **题目类型跨度大**：覆盖偏微分方程、复分析、拓扑学、运筹学等 18 个子领域，不能只靠固定模板。
3. **不能只是单轮提示词调用**：评分明确不鼓励“提示词堆叠或固定模板完成单轮作答”。
4. **必须结构化输出 JSON**：格式错误、接口异常、无法解析会直接按未通过处理。
5. **需要过程解释和学习启发**：不是只输出答案，还要解释推理思路。
6. **决赛需要多智能体协作**：题型识别、solver agent、过程校验、长程推理控制都是重要方向。
7. **不能人工逐题干预**：严禁人工逐题作答、赛后补填、伪造日志或使用未经允许的外部闭源服务代答。

## 4. 推荐技术栈

### 4.1 技术栈总表

| 模块 | 推荐技术 | 说明 |
|---|---|---|
| 核心模型 | Intern-S1 API | 赛题指定模型，负责数学推理和解题 |
| Agent 框架 | lagent、LangGraph、自研轻量状态机 | 官方推荐 lagent，可用于工具调用和智能体编排 |
| 后端语言 | Python | 数学工具、API 调用、数据处理、JSON 输出都适合 Python |
| Web / Notebook Demo | Jupyter Notebook、Gradio、Streamlit、FastAPI + Vue/React | 决赛展示交互系统 |
| 数学工具 | SymPy、NumPy、SciPy、mpmath、NetworkX、PuLP / OR-Tools | 用于符号计算、数值计算、优化问题、图论问题校验 |
| 公式处理 | LaTeX、MathJax、KaTeX、latex2sympy 可选 | 处理数学表达式和展示推理过程 |
| 结构化输出 | JSON Schema、Pydantic | 保证输出格式稳定、可解析 |
| 日志与复现 | SQLite / JSONL / CSV | 保存题目、模型调用、推理过程、答案、校验结果 |
| 评测脚本 | Python + 自定义答案归一化 | 对比模型输出和标准答案，统计正确率 |
| 可视化 | ECharts、表格、流程图、Notebook cell | 展示题型分布、正确率、推理流程和校验轨迹 |

### 4.2 每个技术栈到底是干什么的

#### 1. Intern-S1 API：核心模型，不需要自己训练

Intern-S1 是上海人工智能实验室的科学多模态基础模型。这个赛题明确要求基于 Intern-S1 API 构建数学智能体。

也就是说，你们主要做的是：

```text
设计智能体流程 + 调用 Intern-S1 + 校验答案 + 输出规范结果
```

不是：

```text
收集大量数学数据 + 训练一个数学大模型
```

这大幅降低了算力门槛。你们不需要很多显卡，主要需要稳定调用 API，并把系统设计好。

#### 2. lagent：官方推荐的 Agent 框架

赛题资料中给了官方基线：InternLM/lagent。它是书生体系下的轻量级 Agent 框架。

它可以做：

- 调用大模型。
- 接入工具。
- 组织多轮推理。
- 管理 Agent 行为。
- 构建数学 solver agent。

因为发榜单位直接给了这个基线，建议优先研究 lagent，而不是完全从零开始。

#### 3. LangGraph / 自研状态机：用于更可控的流程编排

如果你们觉得 lagent 不够灵活，可以使用 LangGraph 或自己写状态机。

数学智能体不是一次模型调用就结束，而是可能有这些步骤：

```text
读题
  ↓
题型识别
  ↓
选择解题策略
  ↓
模型推理
  ↓
工具校验
  ↓
答案修正
  ↓
生成解释
  ↓
输出 JSON
```

用状态机可以明确每一步，避免模型自由发挥导致格式混乱。

#### 4. Python：主开发语言

Python 适合这个题，因为：

- 调用 API 方便。
- 处理 JSON 方便。
- 有大量数学计算库。
- 适合写评测脚本。
- Notebook / Gradio / Streamlit 都是 Python 生态。

整个系统可以用 Python 完成，不一定需要复杂前端。

#### 5. SymPy：数学工具中最重要的一个

SymPy 是 Python 的符号数学库。

可以做：

- 化简表达式。
- 求导。
- 积分。
- 解方程。
- 矩阵运算。
- 验证两个表达式是否等价。
- 求极限。

例如模型输出一个答案，你可以用 SymPy 检查：

```text
模型答案是否满足原方程？
两个表达式化简后是否相同？
导数是否正确？
```

这对“过程校验智能体”很重要。

#### 6. SciPy / NumPy / mpmath：数值计算和近似验证

有些数学题很难符号验证，可以做数值验证。

例如：

- 随机取几个点代入表达式。
- 检查等式两边数值是否接近。
- 对优化问题做数值求解。
- 对微分方程做简单数值验证。

这类工具可以帮助系统判断模型答案是否靠谱。

#### 7. OR-Tools / PuLP：运筹学问题工具

赛题提到覆盖运筹学。运筹学题可能涉及：

- 线性规划。
- 整数规划。
- 最短路径。
- 最大流。
- 调度问题。

可以用：

- **PuLP**：线性规划和整数规划上手简单。
- **OR-Tools**：更强大的优化工具。
- **NetworkX**：图论、最短路径、网络流等。

如果做题型路由，遇到优化类问题可以调用这些工具辅助验证。

#### 8. JSON Schema / Pydantic：防止格式错误丢分

评分明确说：如果没有按要求输出结构化 JSON，导致无法判分，视为未通过。

因此必须用结构化输出校验。

建议定义统一格式：

```json
{
  "problem_id": "001",
  "domain": "complex_analysis",
  "answer": "...",
  "final_result": "...",
  "reasoning_summary": "...",
  "confidence": 0.82,
  "verification": {
    "status": "passed",
    "method": "symbolic_check"
  }
}
```

用 Pydantic 校验：

- 字段是否齐全。
- 类型是否正确。
- answer 是否为空。
- confidence 是否在 0-1 之间。

如果模型输出不合法，就自动修复或重新请求。

#### 9. 日志系统：防止不可复现

赛题要求必要日志信息，且严禁伪造日志。建议所有题目都保存 JSONL 日志：

每一道题记录：

- 题目 ID。
- 题目文本。
- 题型识别结果。
- 使用的 solver agent。
- Intern-S1 请求和响应摘要。
- 工具校验结果。
- 最终答案。
- JSON 输出。
- 是否重试。
- token / 时间消耗。

日志不是可有可无，它会影响展示质量和复现性。

#### 10. Gradio / Streamlit / Notebook：做决赛 Demo

决赛要求展示 Web / Notebook Demo。

推荐优先级：

1. **Jupyter Notebook**：最容易展示数学推理过程，适合初期。
2. **Gradio**：快速做 Web 交互，上传题目、输出答案和解释。
3. **Streamlit**：适合做仪表盘，展示正确率、题型分布、日志。
4. **FastAPI + Vue/React**：更正式，但开发成本更高。

如果团队前端经验少，建议用 Gradio 或 Streamlit，不必一开始写复杂 Web 系统。

## 5. 推荐系统架构

```text
数学题输入
  ↓
题目预处理：清洗文本、识别 LaTeX、提取条件与目标
  ↓
题型识别 Agent：判断属于代数 / 分析 / 拓扑 / PDE / 运筹等
  ↓
策略规划 Agent：选择解题路线和可用工具
  ↓
Solver Agent：调用 Intern-S1 进行分步推理
  ↓
工具校验模块：SymPy / SciPy / OR-Tools / 数值代入 / 逻辑一致性检查
  ↓
Verifier Agent：判断答案是否可信，必要时要求重推
  ↓
Explainer Agent：生成学习启发式解释
  ↓
JSON Formatter：输出结构化结果并校验格式
  ↓
日志系统：保存全过程，供复现和展示
```

## 6. 推荐技术路线

### 6.1 总体推荐路线

建议采用：

> **题型路由 + 多步推理规划 + 工具校验 + JSON 稳定输出 + 决赛多智能体协作**

这个题最关键的是正确率，所以要围绕“怎么提高答对率”来设计，不要只做漂亮界面。

### 6.2 第一阶段：跑通 Intern-S1 API 和单题解答

目标：能调用 Intern-S1，输入一道数学题，得到答案。

步骤：

1. 注册并获取 Intern-S1 API token。
2. 阅读书生 API 文档。
3. 写 Python 脚本调用 API。
4. 输入一道简单数学题。
5. 输出答案和简短推理过程。

产出：

- 一个 `solve_one_problem.py` 脚本。
- 能成功调用 API。
- 能保存一次请求和响应日志。

### 6.3 第二阶段：定义 JSON 输出格式

目标：保证所有题都能被评测脚本解析。

建议先定义 Pydantic 模型：

```python
class MathAgentResult(BaseModel):
    problem_id: str
    domain: str
    answer: str
    final_result: str
    reasoning_summary: str
    confidence: float
    verification_status: str
```

然后要求模型输出 JSON。如果模型输出格式不对，自动触发：

```text
格式修复 Agent → 重新整理为合法 JSON
```

这个阶段非常重要，因为格式错会直接丢分。

### 6.4 第三阶段：批量处理 112 道题

目标：从单题走向完整评测集。

步骤：

1. 读取组委会提供的数据集。
2. 为每道题分配 problem_id。
3. 循环调用智能体。
4. 保存每题结果 JSON。
5. 保存每题日志。
6. 遇到 API 失败自动重试。
7. 最终生成一个结果文件。

要特别注意：

- API 调用限流。
- 失败重试。
- 中断恢复。
- 每题结果独立保存，避免跑一半崩了全部丢失。

### 6.5 第四阶段：做题型识别和路由

目标：不同类型数学题走不同策略。

可以先让模型判断题目属于哪类：

| 题型 | 可能策略 |
|---|---|
| 代数 | 符号推导 + SymPy 校验 |
| 微积分 | 求导/积分/极限工具校验 |
| 偏微分方程 | 方程结构分析 + 代入验证 |
| 复分析 | 定理识别 + 关键条件检查 |
| 拓扑学 | 概念推理 + 反例检查 |
| 运筹学 | 建模为优化问题 + OR-Tools / PuLP 求解 |
| 图论 | NetworkX 辅助验证 |
| 概率统计 | 数值模拟 / 公式校验 |

题型路由价值很大，因为它能证明你不是简单单轮调用。

### 6.6 第五阶段：加入过程校验

目标：让系统能发现模型推理中的错误。

校验方式可以分三类：

#### 1. 符号校验

适合：代数、微积分、方程。

示例：

- 化简表达式。
- 检查等式是否恒成立。
- 把解代回原方程。
- 对积分结果求导验证。

#### 2. 数值校验

适合：难以符号化的问题。

示例：

- 随机取点代入。
- 计算误差是否小于阈值。
- 用数值方法求近似答案，和模型答案比较。

#### 3. 逻辑校验

适合：拓扑、复分析、证明题。

示例：

- 检查是否使用了题目没有给出的条件。
- 检查结论是否和已知定理冲突。
- 要求另一个 verifier agent 审核推理链。

### 6.7 第六阶段：设计重试和自我修正机制

目标：如果校验失败，不是直接提交错误答案，而是自动修正。

流程：

```text
Solver 输出答案
  ↓
Verifier 校验失败
  ↓
提取失败原因
  ↓
把失败原因反馈给 Solver
  ↓
要求重新推理
  ↓
再次校验
  ↓
最多重试 N 次
  ↓
输出最佳答案和置信度
```

这能提高正确率，也能体现智能体机制。

### 6.8 第七阶段：生成学习启发式解释

赛题要求“过程解释与学习启发”。解释不能只是把推理链原样输出，而要像老师讲题：

- 先指出题目关键条件。
- 说明为什么选这个方法。
- 解释关键定理或技巧。
- 给出容易错的点。
- 最后总结解题思路。

可以单独设计 Explainer Agent：

```text
输入：题目 + 最终推理 + 答案
输出：面向学生的启发式讲解
```

注意：如果评测只看答案，解释不要影响 JSON 中 answer 字段的稳定性。

### 6.9 第八阶段：决赛扩展为多智能体系统

初赛是单智能体，决赛要多智能体协作。建议设计：

| Agent | 职责 |
|---|---|
| Router Agent | 识别题型，选择 solver |
| Planner Agent | 制定解题计划 |
| Algebra Solver | 处理代数、方程、符号计算 |
| Analysis Solver | 处理微积分、复分析、PDE 等 |
| Optimization Solver | 处理运筹学、优化、图论 |
| Verifier Agent | 校验答案和推理过程 |
| Explainer Agent | 生成学习启发式解释 |
| Formatter Agent | 保证 JSON 格式规范 |

决赛可以展示：

```text
一道复杂题输入
  ↓
Router 判断题型
  ↓
Planner 生成解题路线
  ↓
对应 Solver 求解
  ↓
Verifier 发现某一步有问题
  ↓
Solver 修正
  ↓
Explainer 生成教学解释
  ↓
Formatter 输出 JSON
```

### 6.10 第九阶段：做 Demo 和可视化

Demo 不需要复杂，但要清晰。

建议包含：

1. 输入数学题。
2. 显示题型识别结果。
3. 显示选择了哪个 Solver Agent。
4. 显示推理计划。
5. 显示工具校验过程。
6. 显示最终答案。
7. 显示学习启发式解释。
8. 显示 JSON 输出。
9. 显示日志和耗时。

如果用 Streamlit，可以额外做一个评测页面：

- 112 道题完成进度。
- 各题型正确率。
- 平均耗时。
- 校验成功率。
- 重试次数统计。

## 7. 可做创新点

1. **题型路由的数学智能体框架**  
   自动识别数学子领域，并调用不同 solver agent。

2. **过程校验与自我修正机制**  
   用符号计算、数值代入和 verifier agent 检查推理链。

3. **结构化 JSON 稳定输出机制**  
   通过 Pydantic / JSON Schema 保证结果可评测、可复现。

4. **面向学习启发的解释生成**  
   把模型推理转换成学生能理解的讲解，而不是堆公式。

5. **数学工具增强推理**  
   根据题型调用 SymPy、SciPy、OR-Tools、NetworkX 等工具。

6. **多智能体协作解题架构**  
   Router、Planner、Solver、Verifier、Explainer、Formatter 分工协作。

7. **错误日志驱动的重试策略**  
   校验失败后把错误原因反馈给 solver，而不是盲目重试。

## 8. 数据和评测方案

### 8.1 数据来源

主要是组委会提供的 112 道数学问题，覆盖 18 个子领域。

需要注意：

- 初赛后可能追加更实时、更高难度问题。
- 因此不能把系统写死在这 112 道题上。
- 不能人工逐题干预。

### 8.2 自建开发集

在正式题目外，建议自建一批练习题用于调试：

- 每类题 5-10 道。
- 包含简单题、中等题、容易误判题。
- 用于测试题型识别、JSON 输出和工具校验。

### 8.3 评测指标

| 指标 | 说明 |
|---|---|
| 答案正确率 | 最核心，直接决定 60 分 |
| JSON 可解析率 | 格式错误会导致题目无效 |
| 平均解题耗时 | 影响批量处理和 Demo 体验 |
| API 失败恢复率 | 调用异常后是否能自动重试 |
| 校验命中率 | 工具校验能覆盖多少题 |
| 校验纠错率 | 校验失败后成功修正的比例 |
| 题型识别准确率 | 路由是否合理 |
| 解释质量 | 是否清晰、有启发性 |

## 9. 可行性分析

| 维度 | 评价 |
|---|---|
| 技术可行性 | 较高。指定使用 Intern-S1 API，不需要训练大模型。 |
| 工程难度 | 中等。主要难在流程设计、JSON 稳定输出、工具校验和批量评测。 |
| 算力需求 | 低。主要调用 API，本地只需要普通电脑即可开发。 |
| 数据难度 | 低到中。组委会提供题目，但高正确率需要额外构造调试集。 |
| 展示效果 | 中等偏强。数学推理过程可视化、solver 路由和校验过程比较适合展示。 |
| 创新空间 | 中高。题型路由、过程校验、多智能体协作都能形成亮点。 |
| 最大风险 | 正确率压力大。答案正确性占 60%，如果 Intern-S1 单次调用表现不稳，必须靠校验和重试提高稳定性。 |
| 资源风险 | API 流控和稳定性。需要注意限流、失败重试和日志保存。 |

## 10. 和其他候选题相比

| 维度 | 数学智能体 | 车路云 | 荣耀多智能体 | 太空智算遥感 |
|---|---|---|---|---|
| 算力需求 | 低 | 低 | 中 | 高 |
| 上手难度 | 中 | 中 | 中高 | 高 |
| 工程可控性 | 较高 | 高 | 中 | 中低 |
| 评分清晰度 | 高 | 高 | 中低 | 高 |
| AI / Agent 味道 | 高 | 中 | 很高 | 高 |
| 最大瓶颈 | 正确率 | 仿真与算法 | 系统抽象与稳定性 | 训练与部署 |
| 是否适合新手 | 较适合 | 较适合 | 一般 | 不太适合 |

这个新题相比太空智算，最大优势是：**不需要本地训练大模型，不需要国产芯片部署，算力门槛低很多。**

相比荣耀多智能体，它的优势是：**任务边界更清晰，评分更明确，有指定模型和官方基线。**

相比车路云，它更贴近“AI 智能体”和数学推理，但展示效果和社会应用场景可能不如车路云直观。

## 11. 推荐原型功能清单

1. 支持输入数学题。
2. 自动识别题型和数学子领域。
3. 自动选择 solver agent。
4. 生成解题计划。
5. 调用 Intern-S1 进行推理。
6. 调用数学工具进行校验。
7. 校验失败后自动重试和修正。
8. 生成学习启发式解释。
9. 输出严格 JSON。
10. 保存完整日志。
11. 支持批量处理 112 道题。
12. 提供 Web / Notebook Demo。
13. 展示正确率、题型分布、耗时和校验统计。

## 12. 新手学习顺序建议

如果你们没有数学智能体经验，建议按这个顺序学：

1. 阅读 Intern-S1 API 文档，跑通一次 API 调用。
2. 学 Python requests / SDK 调用方式。
3. 学 JSON 格式和 Pydantic 校验。
4. 做一个单题求解脚本。
5. 做批量读取题目和保存结果。
6. 学 SymPy 基础：化简、求导、积分、解方程、代入验证。
7. 做题型识别 prompt。
8. 做题型路由和不同 solver prompt。
9. 做 Verifier 校验和重试机制。
10. 做日志系统和断点续跑。
11. 用 Streamlit / Gradio 做 Demo。
12. 决赛再扩展多智能体协作和可视化。

## 13. 推荐项目命名与包装方向

可包装为：

- **“MathRoute-S1”：基于 Intern-S1 的题型路由与过程校验数学智能体**
- **“ProofPilot-S1”：面向高等数学问题的多智能体推理与校验系统**
- **“启思 S1”：具备学习启发与自校验能力的数学解题智能体**

包装重点：

1. 不是简单问答，而是“题型识别—推理规划—工具校验—自我修正—结构化输出”。
2. 不是只追求答案，还强调学习启发式解释。
3. 初赛重正确率，决赛重多智能体协作和交互 Demo。
4. 使用官方 Intern-S1 API 和 lagent 基线，降低算力门槛。

## 14. 适合什么团队选择

适合：

- 团队想做 AI Agent，但不想承担大模型训练和国产芯片部署风险。
- 团队 Python 能力较好。
- 有数学基础较强的成员，能理解高等数学、分析、代数、运筹等题目。
- 有同学愿意做评测、JSON 格式、日志和工具校验。
- 希望题目边界明确、评分清楚。

不太适合：

- 团队数学基础较弱，无法判断模型推理是否合理。
- 团队只想做炫酷界面，不愿意打磨正确率。
- 团队无法稳定调用 API 或不愿意处理格式、日志、重试等工程细节。

## 15. 综合判断

这是一个非常值得重点考虑的新题。它的优点是：

1. 算力门槛低。
2. 学生赛道。
3. 任务边界清楚。
4. 评分中 60% 是客观正确率，努力方向明确。
5. 有官方模型 API 和基线支持。
6. 非常贴近“智能体推理链设计”。

它的主要风险是：

1. 正确率压力大。
2. 题目数学难度可能较高。
3. 不能只靠 prompt，需要做题型路由、校验和重试。
4. 如果团队数学成员不足，可能难以判断和优化推理质量。

如果团队有一定数学基础和 Python 工程能力，我认为它的综合推荐度可以排在 **车路云之后，荣耀和太空智算之前**。
